Performance measurements

Reproducible local measurements, separated by what each benchmark actually includes.

Recorded for version 0.1.0 on September 24, 2026. Environment: AMD EPYC 9V74 80-Core Processor, Linux x86-64, GCC 14.2.0, glibc 2.41, CPython driver 3.13.5. CMake Release with supported LTO enabled. These are warm local-container results, not hardware-independent guarantees.

Native text store, 64 MiB

The native benchmark starts with 64 MiB of ASCII text in 80-byte lines. It performs 20,000 random insert/delete pairs, 20,000 line/byte seek pairs and 100,000 contiguous insertions. The table reports the median of three runs, taking each metric's median separately.

Backend key round trips

A separate standard-library Python driver opens a file through the real JSON Lines backend and sends 300 editing requests with a 40-row, 120-column viewport. Measurements include Python serialization/parsing, local pipe IPC, native editing and snapshot generation. They exclude GUI/terminal painting and input-method latency.

Highlighting is deliberately disabled above 16 MiB. Consequently, the 64 MiB row is not a same-feature workload as a small highlighted buffer. Small differences between these rows do not establish that larger files are intrinsically faster.

Reproduce

cmake -S . -B build-release -G Ninja     -DCMAKE_BUILD_TYPE=Release -DPython3_EXECUTABLE=/usr/bin/python3
cmake --build build-release -j
./build-release/bench_text 64 20000
/usr/bin/python3 bench/measure.py build-release > bench/results-local.json

Inspect the actual benchmark sources before changing workloads. The measurement driver runs the text-store benchmark three times and emits environment details plus native and protocol measurements. Download the recorded JSON data.

Interpretation and remaining bottlenecks

These results support the claim that local editing avoids a full-document copy on each key in this implementation. They do not establish superiority over GNU Emacs, the original simplepypad, another text structure or a Python GUI. No controlled baseline comparison was run.

Undo history and additions storage grow with edits. Loading a file creates transient copies. A whole-buffer Python formatter still allocates the whole text and blocks the backend. Lexer state propagation, long-line navigation, system scheduling and filesystem latency can dominate different workloads. Native code alone does not make those costs disappear.

Version scope

The benchmark records above were produced for 0.1.0. They are retained as historical evidence, not measurements of 0.1.1 terminal rendering. The 0.1.1 colour adapter caches the computed palette and retains row-difference output; no new end-to-end speed comparison is claimed.
