Architecture

One owner for editable state, native hot paths, and a transport boundary between editing and presentation.

Process and module boundary

ComponentImplementation and responsibility
Text storesrc/text.c: UTF-8 piece table, implicit randomized treap, byte/character/line indexing.
Editorbuffer.c, commands.c: file buffers, point, mark, kill ring, undo, minibuffer, keys and pane layout.
Rendering modelsyntax.c, view.c: lexical-state cache and bounded visible viewport snapshots.
Python bridgepython.c: embedded CPython with a small native API; no frontend objects.
Transport and protocoltransport.c, protocol.c, main.c: JSON Lines, pipes/socketpairs and local Unix sockets.
Terminaltui.c: termios, ANSI escape sequences, UTF-8 input, bracketed paste, changed-row rendering.
GUIgui_x11.c: Xlib, XIM input, FontSet rendering, double buffering, mouse and clipboard. Links transport and Xlib, not the core or CPython.

Text storage and expected cost

The original file is immutable storage. New text is appended to a separate allocation and referenced by pieces in an implicit treap. Each node aggregates byte, Unicode-code-point and newline counts. Pieces are split at UTF-8 boundaries and capped at 4,096 bytes. Expected tree traversal is logarithmic in piece count; bounded scans inside pieces find exact locations. Randomized balancing is not a worst-case deterministic bound.

Contiguous insertions can extend the most recent piece. Local editing does not copy the entire file. Undo stores changed text and edit coordinates rather than full-buffer copies. It is still possible for the additions store, fragmented pieces and unlimited undo history to consume substantial memory during a long session.

Views, long lines and highlighting

A snapshot contains only visible rows, not the complete buffer. The row limit is 200 and the column limit is 500. Line/column checkpoints avoid repeatedly scanning an entire long line on adjacent keystrokes. Edits before a checkpoint invalidate it. Text uses Unicode scalar boundaries; display columns use wcwidth, not a full grapheme or text-shaping engine.

Major-mode plugins supply syntax kind and keyword sets. The C scanner produces token spans and caches multiline state. This is incremental lexical highlighting, not a parser or language server. Highlighting is disabled above 16 MiB per buffer or 256 KiB per displayed physical line. A jump to an uncached line can still scan preceding lexical state; there is no hard real-time latency guarantee.

Backend ownership and concurrency

The backend is a single-threaded state machine. Every client sends the same operations. Standalone frontends spawn a private backend over a socketpair; a persistent server accepts multiple clients through a Unix socket. There is one editor state, not independent per-client point, minibuffer or window trees. A GUI attaches to the editing service, not by scraping terminal escape sequences.

Python callbacks are synchronous. A slow hook, formatter or user command blocks native interaction until it returns. Built-in movement and insertion do not require Python execution, except when the user registers a corresponding hook. Do not describe this architecture as asynchronous merely because the GUI has its own process.

Rendering tradeoffs

The terminal caches rendered rows and writes only changed rows. The GUI paints a double-buffered visible frame, rather than maintaining a second document model. Idle polling checks shared backend state roughly every 200 ms; direct input requests receive their own immediate snapshots. Xlib was selected for a native buildable frontend with a small dependency surface, not because a C-versus-Python GUI benchmark established a universal winner.

Source origin

This is a rewrite of the supplied simplepypad project, which had Python/Tkinter and curses presentation code. Its MIT copyright is preserved. Old plugins that accessed those widget objects are not source-compatible. No GNU Emacs code, Lisp runtime or third-party Emacs package is bundled.
